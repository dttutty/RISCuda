# 每个请求一次 CUDA Graph 的公开算术评测

[English](autonomous-public-200.md) | **简体中文** · [验证索引](../../VALIDATION.zh-CN.md)

RISCuda 单次执行图组与原版 Qwenputer 均答对 **195/200（97.5%）**。
在**双方答案精确且正常 EOS 的 192 对请求**上，请求耗时降低 **41.48%**，
耗时比为 **1.7088×**（Qwenputer/RISCuda）。按配对题目进行 2000 次重采样 bootstrap，
耗时降低比例的 95% 区间为 **35.98%–45.94%**。全部 **200 个原生请求均只提交一次
主机 CUDA Graph**，包含实际提示词预填充、生成、RISC-V 计算器执行与反馈，直到 EOS 或指定上限。

| 数据集 | 原生组精确答案数 | Qwenputer 精确答案数 | 双方精确且正常 EOS 的配对数 | 原生组平均秒数 | Qwenputer 平均秒数 | 耗时降低 |
| --- | --- | --- | --- | --- | --- | --- |
| 合成 `arith` | 38/40 | 39/40 | 38 | 6.68 | 10.06 | 33.61% |
| DeepMind `mul_big` | 39/40 | 39/40 | 39 | 4.29 | 7.27 | 40.95% |
| DeepMind `div_big` | 39/40 | 39/40 | 38 | 6.59 | 8.52 | 22.57% |
| DeepMind `mul_div_multiple_longer` | 40/40 | 40/40 | 39 | 37.85 | 69.24 | 45.33% |
| DeepMind `add_or_sub_big` | 39/40 | 38/40 | 38 | 6.43 | 10.49 | 38.68% |

耗时列使用每行双方正确完成的共同子集。这 192 个请求的累计耗时为 RISCuda **2392.70 s**、
Qwenputer **4088.59 s**。计入全部失败和截断后，累计耗时分别为 **3070.00 s** 和
**5304.83 s**，降低 **42.13%**。这些数值是逐请求时长之和，不是两个并行 GPU 作业的总运行时间。
每组均有五次预算截断，其中一次已有正确答案；每组均有 194 个请求同时满足答案精确和正常结束。

总准确率相同，但失败样本不同。原生组在 `arith-18` 上失败，Qwenputer 成功；
原生组在 `add_or_sub_big-6890` 上成功，Qwenputer 失败。
原生组的 `mul_div_multiple_longer-7815` 答对但达到文字预算；
Qwenputer 对应的答对却截断样本为 `div_big-7961`。
双方均误解了 `add_or_sub_big-8541` 中的减法。
全部错误答案、反复调用和截断续写均保留在证据中，未从全部请求的累计耗时中移除。

**139/200 对**的完整文字 token 流一致。尽管共享 BF16 参数，静态缓存和注意力执行的数值差异
仍可能改变 greedy 续写，因此不声称解码逐位一致。
在**文字完全相同、答案精确且正常结束的 138 对请求**上，原生组耗时降低 **41.31%**
（耗时比 1.7038）。这一额外子集检查表明，整体提升不能仅用答案长度不同来解释。

## 配置与计时

模型与 [ModelScope 模型卡](https://modelscope.ai/models/Spartan1925/Qwen3.5-4B-Qwenputer)
使用同一份 **Qwen3.5-4B-Qwenputer BF16** 检查点；已重新将本地全部八个分片及推理和分词器配置
与该镜像进行哈希核对。缓存版本为 `2d9068508f2b680badb7abcded96fdd107e9ba5d`。
保留原作者的五组数据、种子 0、每组 40 题、提示词 ID、工具 schema、`NUDGE`、boxed 答案后缀、
greedy 解码和关闭 thinking 的设置。标准答案未进入模型输入或 GPU 执行。
原生组使用与原作者相同的 C 源码和计算器限制，以原生十进制行服务替代权重内执行器。

markov 上两张已确认空闲的 RTX A6000 48 GB GPU 分别运行不重叠的题目分片。
每个配对始终在同一张 GPU 上运行，两组顺序交替。
环境为 Torch 2.9/CUDA 12.8、Transformers 5.21.1、Triton 3.5、Zig 0.14.1 和 CUDA 工具链 12.9，
未安装可选的 causal-conv1d 和 FLA。两组均使用 batch 1 和 4096 个文字 token 的预算；
原版 Qwenputer 另保留 200000 个芯片 token 的上限。原生控制器最多允许 64 次调用。
完整命令、GPU UUID、CPU 亲和性和源码哈希均在证据中。

原生推理使用已捕获的静态缓存解码和 GPU 条件控制器。
原版 Qwenputer 保留上游主机解码循环与 Triton 电路执行器。
长度相同的提示词分组复用地址稳定的输入存储，不添加填充，并在启动时用真实问题检查输入替换。
预填充在静态底层存储上返回与提示词等长的 KV 视图；每个捕获长度组的 logits 均与原版预填充逐位一致。
测量包含实际预填充、全部生成、计算器执行和反馈，不包含模型加载、构建、预热、捕获、执行图实例化、
初始缓存重置、最终轨迹下载和 CPU 参考检查。

这项对比针对完整运行时配置。加速包含语言模型捕获推理、静态缓存和原生计算器执行的共同影响，
不能仅归因于取消 CPU 调度。原生阶段计时累计为 0.718 s；基线芯片 token 阶段累计为
807.72 s，共 2513123 个芯片 token。二者计时边界和生成工作量不同，
因此商值不能作为独立工具加速比。每个题目、每组各测一次，并非吞吐量或推理服务并发研究。
该闭环使用固定 C 计算器，不支持任意 MicroPython 路由。

## 独立验证与恢复

全部 **400 条保存的请求均通过原版固件轨迹或前缀重放**、精确答案重新评分、提示词检查及源码和状态验证。
每个原生请求的启动次数均为一次；每次原生计算器调用的虚拟机状态和客户机错误均为零。
有 18 次调用与无界 Python 算术参考程序结果不同，因为 C 固件会按寄存器限制拒绝复杂表达式。
这些错误与原版固件完全一致。工具级错误与虚拟机故障是不同情况。

初始评测代码提交为 `d0a9d75`。一个分片完成 76 对请求后，运行后的 Python 参考检查器
因 `abs(...)` 抛出 `NameError` 而停止，此时 GPU 请求已经完成。
仅修改验证逻辑的提交 `274233a` 在同一 GPU 上续跑剩余 24 对，保留全部 152 条已记录数据；
未记录的那次请求因计时尚未保存而重跑，其 token 流和强制输入标记与中断前完全一致。
AST 和源码检查确认推理代码未变。审计修复 `1588c95` 还识别原固件的容量错误。
初次失败的分段、源码版本和恢复清单均保留，不将其报告为初次运行正常退出。

## 单次启动的采样证明

另一次不计入评测耗时的 Nsight 采样使用真实公开题目 `add_or_sub_big-6634`。
GPU 对 `abs(20412938679033416 - (-0.4))` 返回 `error`；
Qwen 随后生成 `20412938679033416 + 0.4`，收到 `20412938679033416.4`，最终答对。
两次工具调用、错误反馈和模型续写均在一个根执行图内发生。
其 token 与未采样的计时请求完全相同，48 个由固件生成的反馈 token 通过原版 CPU 参考重放。

| 采样请求期间的观察项 | 数值 |
| --- | --- |
| 主机 `cudaGraphLaunch` 调用 | 1 |
| 最终主机 `cudaStreamSynchronize` 调用 | 1 |
| 主机 kernel 启动 API 调用 | 0 |
| 主机 memcpy API 调用 | 0 |
| 设备根执行图活动 | 1 |
| 解码前向次数，取自最终状态 | 472 |
| 工具调用次数，取自最终状态与参考重放 | 2 |
| 设备执行图耗时，包含预填充 | 14.290827561 s |

CUDA Graph 内含多个设备端 kernel。Nsight 使用整图级跟踪并关闭事件跟踪，不枚举内部 kernel 或拷贝节点。
采样时包装层耗时 18.358 s，未采样的计时请求为 14.341 s；采样开销不计入评测比较。
仍需要 CPU 初始化、提交和最终收集。全部 CPU 数学验证都在 GPU 完成之后进行，不会反馈给模型。
